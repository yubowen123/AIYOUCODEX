# 原生分页历史的定向恢复

本工具用于已确认的 `thread_settings_applied` 重复序号冲突，不是日常清理器，也不会随增强层启动或自动运行。

## 已验证的故障机制

在本次验证的 Codex app-server 0.153.4 中，原始 JSONL 可以保留完整聊天，而分页历史 SQLite 索引因 `expected ordinal N, got N-1` 停止推进。重复记录若属于设置元数据，不等于用户消息重复或已被删除。

后续区间存在多处冲突时，原生补建事务会整体回滚。只调整第一处游标不能恢复完整历史；工具不再暴露这种修改入口。

## 恢复流程

1. 用 `scripts/repair-thread-history-index.mjs audit <codex-home> <thread-id>` 核验当前卡点。它要求明确的本机任务 UUID、分页模式、同任务设置记录以及连续的下一轮边界；未知类型直接拒绝。
2. 用该脚本的 `backup` 操作创建新的私有备份目录。保留完整原始前缀的 SHA-256 和 SQLite 一致性快照，不能用普通文件复制替代在线 SQLite 备份。
3. 人工复核后续区间中的全部冲突，形成 `[{offset,bytes,ordinal}]` 清单。禁止按标题去重或忽略消息记录。
4. `scripts/probe-history-recovery.mjs` 在备份目录的隔离环境中工作。`read` 阶段复制快照，只在**可丢弃的读取副本**中把已核验的设置重放标记替换成等长空白；保留所有消息及字节位置。原始聊天文件不变。
5. 同一工具的 `resume` 阶段使用当前安装的官方 app-server 补建副本索引。只调用初始化、读取和恢复历史接口，不发送 `turn/start` 或生成请求。`verify` 阶段通过原生 `thread/items/list` 抽查指定用户消息。
6. `scripts/merge-recovered-history.mjs plan` 检查：原始备份与实时文件前缀一致；读取副本除了设置标记外完全一致；原生索引到达快照末尾；原有索引记录逐字段不变。`apply` 才会在事务中补入**这一条任务**的缺失记录，并用精确状态比较更新游标。并发变化、原有记录变化、唯一键冲突或快照不完整都会拒绝/回滚。
7. 真实 Codex 分页读回、新写入后的游标推进、历史锚点和原生日志均须核对。数据库修复不代表已经检查了用户当前窗口的缓存画面。

以上脚本需要现代 Node.js 的 `node:sqlite`（本次 Node.js 26.3.1）。协议结构以当前安装版生成的 schema 为准，换版本后应先复核，不应盲目自动执行。

## 边界与回滚

- 不重签安装包，不重启其他任务，不修改任何原始聊天内容，不上传私有备份。
- 合入操作只增加经官方读取器重建的记录；既有记录必须保持一致，不按标题合并不同任务。
- 私有备份位于 Codex 用户目录下的 `repair-backups/`。不得直接把整个旧 SQLite 数据库覆盖回正在运行的应用，否则会影响备份后其他任务的数据。
- 原始文件中的历史设置标记仍保留，因此未来删除并全量重建历史数据库，或宿主再次产生同类序号错误时，仍需要重新诊断。这是历史索引恢复，不声称已修改官方写入器或永久消除宿主缺陷。
- 定向验证：`node --test test/history-index-repair.test.mjs test/history-recovery-merge.test.mjs`。
